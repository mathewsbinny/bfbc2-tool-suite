# BFBC2 Tool Suite: deep scan, 2026-11-15

> **Archived** (round KB1s, 2026-11-28): a dated record, not current truth. Outcome and what supersedes it:
> [README.md](README.md) in this folder.

Target: the suite's main checkout at `main` 9104618. This was a read-only scan. Nothing in the repository was changed: `git status` was clean before and after the test runs.

## Summary

The suite is a large body of reverse-engineering tooling: about 69,500 lines across 203 Python files, 5 C# files and 1 C++ file. It is unusually disciplined for a hobby project. ruff (F/E/W/B/I/UP/SIM) and mypy (`check_untyped_defs` everywhere, with a strict list) are enforced in the quick tier. There is one path finder (`core/bfbc2core/paths.py`) and one `sys.path` bootstrap (`suite_paths.py`). Binary readers check their bounds (`shaderdb._Reader`, `dbx.parse`), and the Xenos translator fails loudly. Every CLI shares error and log handling. 65 quick tests pass. The game tier compares the suite against DICE ground truth.

The weak spots are in three areas:
- **Writes into the game copy.** NavKit and stock-MP installs copy into the game folder non-atomically and can stop half-way.
- **Caches and swallowed errors.** A few caches can be silently poisoned or go stale, and several broad `except Exception: continue` blocks swallow errors.
- **Structure.** The modules are very large (navbuild 1,871 lines, aptgraft 2,441). There are still three binary DBX codecs, and core still depends on the NavKit tool layer. The consumer project reaches into private names 26 times.

Most structural findings of the 2026-11-09 architecture audit are still open.

## 1. Reliability & correctness: 7/10

**Justification.**
- **Binary formats are bounds-checked.** `shaderdb._Reader.count/need` (shaderdb.py:393-416) refuses counts that cannot fit. `ShaderDb._parse` rejects trailing bytes and out-of-range table indices (shaderdb.py:268-274). `dbx.parse` refuses truncated NUMBERS, value and container data (dbx.py:136-148). The stock-MP build refuses to go on unless the DBX writer reproduces the original exactly (pipeline.py:372-373).
- **Converters are checked against DICE's own data.** The fair-port test passed 7 partitions against DICE in this run.
- **Correctness gaps are real but narrow.**
  - The test runner's "DICE original" choice disagrees with `navkit.original_file`. It can select stock-MP's file as DICE's (finding C5).
  - `dbx.value` keeps DbxEdit's print heuristic. A 4-byte float whose top byte is 0 (denormals and very small floats) comes back as an integer string (dbx.py:254-257), so semantic callers can read wrong numbers.
  - The duplicated `typ`/`depth` check in texture.convert (texture.py:226 and 235) is dead code. It is harmless, but it is a sign of copy-paste.

**Top improvements.**
1. Make `run_tests.dice_pathdata_files` call `navkit.original_file`, and add a test with both `.opfor-orig` and `.opfor-stockmp-orig` present.
2. Add a typed reader, `dbx.number_values(e) -> list[int|float]`, that decodes by field schema rather than the print heuristic. Keep `value()` for XML parity only.
3. Add the missing-key branch of the `required` loop and dead-code checks: dbxport.py:1281 `if '/' not in r and resolve is None: pass` is a no-op whose intent is unclear.

## 2. Robustness: 6/10

**Justification.**
- **Good:**
  - Navigation side files are written atomically (navtune.py:180-186).
  - The navdata caches use per-process temp files plus `os.replace` (navdata.py:156-160, 170-173).
  - Stock-MP builds into `out.partial` and swaps in, and the report is written last (pipeline.py:336-405). `install --apply` checks every marker before writing anything (stockmp.py:118-129).
  - FbrbTool writes the manifest last, so a partial unpack is never mistaken for a finished one (FbrbTool.cs:145), and it guards against path traversal (FbrbTool.cs:111-123).
- **Bad:**
  - Writes into the game copy are plain `shutil.copyfile`, and a multi-file install can stop half-way (C1, C2).
  - The mesh-viewer index caches a silently incomplete result (C3).
  - Terrain unpacks have no source stamp (C4).
  - Settings and cache JSON files are written non-atomically and read without a fallback (C6).
  - About 100 `open(...,'w'/'wb')` write sites against 20 `os.replace` calls in non-test code.

**Top improvements.**
1. Add one `atomic_write(path, bytes)` and one `atomic_copy(src, dst)` helper to core (temp file in the same folder, then `os.replace`). Use them for every write into `game\` and for every settings or cache file.
2. Make `stockmp install --apply` transactional: copy every file to `dst.opfor-stockmp-new` first, then replace all of them. On failure, roll back from the backups.
3. Stop caching results built under `except Exception: continue`. Record skipped inputs and either refuse to cache or put them in the cache key.

## 3. Readability & clarity: 6/10

**Justification.**
- **Strengths:** Docstrings and READMEs are thorough and explain why, not only what. Examples: `paths.py:1-50`, `dbxport.port`'s parameter list (dbxport.py:1214-1232) and the enum-mapping rationale (dbxport.py:345-361).
- **Long functions and modules:** Several functions run to hundreds of lines (`navwalk.walkable` ~285, `navbuild.stage` ~271, `navbuild.build_graph` ~166). Several modules exceed 1,500 lines (aptgraft 2,441, renderqa 1,986, navbuild 1,871, dbxport 1,695).
- **Inline commentary as history:** Comments mix dates, playtest notes and history into the code (dbxport.py:345-361, navkit.py:552-556 duplicates a comment line). This reads more like a lab notebook than current-state documentation.
- **Other clarity issues:** Long lines are allowed (E501 ignored). Many names are one or two letters (`P`, `L`, `T`, `o`, `B`). xenos.py's `Obj` makes every IR attribute `Any` (xenos.py:44-52).

**Top improvements.**
1. Split the four largest modules along the seams the architecture audit already named. For example, move aptgraft's Onslaught-timer recipe out of the generic APT library.
2. Move dated investigation notes into the FORMAT/DESIGN documents. Keep a one-line "why" in the code.
3. Replace the xenos `Obj` attribute bag with dataclasses per instruction kind, so mypy can check the translator.

## 4. Maintainability: 6/10

**Justification.**
- **Tooling:** ruff and mypy are enforced on every folder, and about 45 modules are on mypy's strict list (pyproject.toml:44-77). The quick tier runs before every commit.
- **Mutable module globals that drive behaviour:** `ORDER_IDS` decides which order nodes `prune_order_nodes` drops (navbuild.py:139, 1642). Other modules reach in and clear it (navvehicle.py:580, 588). That is not thread-safe and depends on call order.
- **Three binary DBX codecs:** core `dbx.py`, `culltree.py:74-270` and `stockmp-ai/dbxbin.py:211-230`.
- **Duplicate locators:** five locator wrappers still exist (navkit, menucommon, shaderdb, navparity, navvehicle `opfor_root`).
- **Duplicate install-marker logic:** navkit.py:77-99, stockmp.py:84-170 and run_tests.py:53-68 each implement it separately, and they already disagree (C5).

**Top improvements.**
1. Return a `BuildResult` (stats plus the order-ID set) from `navbuild.build` instead of using module globals. This is QUALITY_AUDIT plan item 3, still open.
2. Fold culltree's and dbxbin's codecs into core `dbx` (byte-identical mode with the string order kept, as DbxEdit does). Expose a public `put_varint`.
3. Add one `bfbc2core.install` module (backup, marker, original lookup, atomic copy) and use it from navkit, stock-MP and the test runner.

## 5. Reusability: 5/10

**Justification.**
- **Not a package:** Every tool is a script that changes `sys.path` (`suite_paths.use`, suite_paths.py:61-66). Top-level module names are generic and shared across folders (`config`, `mesh`, `texture`, `terrain` twice, `pipeline`), and mypy has to run one folder at a time because of it (pyproject.toml:4).
- **Consumer uses private names:** OPFOR's `src\tools` uses private suite names at 26 sites: `meshview._layout` ×14, `dbx._put_varint` ×8, `mesh._pair_by_kind` ×2, `terrain._visual_terrain`, `meshview._surfaces`. That is up from about 14 in the 2026-11-09 audit.
- **Good library-shaped modules:** `paths.py` needs only `os` and `sys`, and `fbrb.py` and `dbx.py` are small and clean.

**Top improvements.**
1. Make the private helpers OPFOR uses public (`dbx.put_varint`, `meshview.layout`, `mesh.pair_by_kind`). Add a test that fails when OPFOR imports a `_name`.
2. Turn `core` into an installable package (`pip install -e core`) and namespace the tool folders (`bfbc2tools.navkit...`) so that generic names cannot shadow each other.
3. Separate library code from CLI drivers in navkit.py. It is both the CLI and the library everyone imports (`Project`, `prepare`, `find_tool`).

## 7. Overall software architecture: 6/10

**Justification.**
- **Sound layer idea:** formats in core, converters, then tools and GUIs. Path discovery is centralised (paths.py) and every CLI shares the error boundary (`errors.guard`).
- **Core depends on the tool layer:**
  - `core/bfbc2core/level.py:41,166` puts NavKit's folders on `sys.path` and imports `navkit` to prepare a level.
  - `navdata.py:35` and `pick.py:18` reach into NavKit's tools.
  - This is the `core ↔ navkit ↔ navkit/tools` cycle reported on 2026-11-09, unchanged.
- **Wrong-direction dependencies:** generic converters depend on GUI-adjacent modules (`granny` → `meshview`, bf1943-import → `meshview.Index`).
- **Hidden behaviour in the quick tier:** the "no game data" tier silently reads game data when it exists (the fair test).

**Top improvements.**
1. Remove the core→navkit edges. Inject a `prepare` callback into `level.load`, and move `area_cells` and the HPD readers that core needs into core.
2. Add the layer-check test proposed in ARCHITECTURE_AUDIT 8.4, so new back-edges fail the quick tier.
3. Split the fair test's quick variant into a separate `game-light` tier, so `quick` means "no game data" and stays fast.

## Suspected findings (lower confidence)

- **S1. Concurrent builds.** `navbuild` module globals (`ORDER_IDS`, `*_STATS`, navbuild.py:138-188; `navislands.TERRAIN_IDS`) are cleared by `reset_stats()` at the start of each build. Two builds in one process at once would corrupt each other's pruning. This would happen if a GUI ran a build on a worker thread while another ran, or if navvehicle cleared `ORDER_IDS` (navvehicle.py:580/588) during a build. I did not confirm that any GUI runs builds concurrently.
- **S2. Pickled NavData cache.** The cache is keyed by `CACHE_VERSION` plus the file's stat and the terrain fingerprint (navdata.py:112-115). A change to `NavData`'s fields or to the kymesh/navdiff logic without bumping `CACHE_VERSION` would load stale objects without an error.
- **S3. DbxEdit attribute count.** `DbxEdit.WriteElement` packs `Kind << 4 | Attributes.Count` with no check for 15 or fewer (DbxEdit.cs:226). The Python writer refuses more than 15 (dbx.py:192-193). An XML import with 16 or more attributes would corrupt the kind nibble silently. No game element is known to have that many.
- **S4. `dbx.to_xml` bool branch.** It reads `data[pos + 1]` without a bounds check (dbx.py:357), and an out-of-range string index raises `IndexError`, not `ValueError`. Callers that catch only `ValueError` (for example `Templates`, which also catches IndexError, but others may not) could crash on damaged files.
- **S5. Mesh-viewer index signature.** It uses `int(os.path.getmtime(b))`, which truncates to seconds (meshview.py:87). A bundle rewritten within the same second with the same size would not invalidate the index. This is unlikely.
- **S6. Asserts as runtime checks.** `assert entry is not None` and `assert lvl_file is not None` in `pipeline.build` (pipeline.py:367-369) are skipped under `python -O`, which would turn a clear error into a `TypeError` further on. This was accepted in QUALITY_AUDIT.

## Methodology

- **Read:** README.md, ARCHITECTURE_AUDIT.md and QUALITY_AUDIT.md (status, scores, open items), pyproject.toml, run_tests.py and tests/test_types.py. Read closely:
  - core: `dbx.py`, `errors.py`, `paths.py`, `fbrb.py`, `level.py` (load, heightfield_of), `navdata.py` (caches); `suite_paths.py`;
  - dbxport (Templates, `port`, helpers);
  - shaderdb (model, reader, writer, level_meshes); xenos.py header; xenos_hlsl (error paths);
  - navkit.py (original_file, Project, prepare, ini handling, sample_run, install / restore, detailed cache); navbuild's global state;
  - stock-MP pipeline (build, swap_in, check_report) and stockmp install;
  - console-convert texture.py;
  - Map Inspector; Studio save paths;
  - meshview Index; bf1943import write path;
  - DbxEdit.cs (codec, import / edit / fixslots); FbrbTool.cs (read, unpack, pack, BIG).
- **Consumer:** Grepped OPFOR `src\tools` for private suite names, and OPFOR's `src\dll\opfor.cpp` to rule out a log-truncation hypothesis.
- **Ran:** `run_tests.py --list` and `run_tests.py quick`. Ran coverage over the quick-tier Python scripts with `COVERAGE_FILE` in the scratchpad. Grep scans for write sites, broad excepts, duplicate helpers and module globals.
- **Not done:** the game and full tiers, and the GUIs with a window. aptgraft, navwalk, navsample_offline, havokport, granny and the harness were not read line by line; their scores rest on sampling, coverage and the earlier audits.

## Fixed after the scan (2026-11-15)

`tests/test_deep_scan_fixes.py` (quick tier) unless noted:
