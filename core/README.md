# core

The suite's shared Python package, `bfbc2core`: the game's data formats, the level loader and the 3D view
that the 3D tools are built on. Python 3.12+ (the suite's, `pyproject.toml`) with `numpy`, and the suite's Rust core
`bc2_native` in this folder (`python rust\build_native.py --download`, or build it: the suite's README, "The Rust
core"): the formats below run in it. The view also needs `moderngl`, `glfw` and `imgui-bundle`.

| Module | What it does | Checked by |
|---|---|---|
| `dbx.py` | reads binary `.dbx` files into an element tree and writes DbxEdit's XML, from `bfbc2-dbx-tools/FORMAT.md`; `parse_many` / `to_xml_many` for many files; `write` (a tree back to a binary file). Runs in the Rust core (`bc2_native`, `../rust`; required: the Python reader and writer were retired on 2026-11-18, round F1a) | `tests/test_dbx.py`: the XML identical to DbxEdit's on all 31,404 fingerprinted files; `tests/test_dbx_native.py`: the reader's answers the retired Python's (recorded: `dbx_golden.json`, `dbx_golden_corpus_*.json`) on every corpus file; `tests/test_dbx_write_native.py`: the writer's bytes the Python writer's on every corpus file, as read and edited |
| `terrain.py` | terrain height fields (`.Heightfield-000.res`): heights, exact height at any point, a mesh. Runs in the Rust core (required since round F1a) | `tests/test_terrain.py`: within 4.5 cm of the in-game terrain for 99.9 % of 40 million samples (13 levels); `tests/test_geometry_native.py`: bit for bit the retired Python reader's answers (recorded: `geometry_golden.json`) on every height field of the game copy |
| `water.py` | water meshes (`.Water.Mesh.res`) and each triangle's shader (from `.Water.res`). Runs in the Rust core (required since round F1a) | `tests/test_water.py`: all 36 levels; `tests/test_geometry_native.py`: the retired Python reader's answers (recorded) on every water file of the game copy |
| `collision.py` | a level's collision: which Havok packfile each blueprint uses (NavKit's `havok_index` and `mesh_aliases`) and its triangles (`levelobjects.triangles`). Runs in the Rust core (one walk, all cores; required since round F1a: the Python path through NavKit's functions retired) | `tests/test_geometry_native.py`: the retired Python path's answers (recorded) on every packfile of the game copy and the index of every prepared level |
| `xmlinst.py` | the `<instance>` elements of a converted level partition (type, guid, body) and a field's reference (`field_ref`), whatever the attribute order (DICE writes `guid` / `ref` first, Napisal `type` / `name` first); used by NavKit's `levelobjects.py` and `ordercheck.py` | output identical to the old readers on the 13 campaign levels and ONS_MP_004 (2026-10-20) |
| `level.py` | a level: entities (types, transforms, blueprints, teams, player types), static-group members, world-space collision, areas and routes, terrain and water; prepares a level on first use; `geometry=False` reads only the entities, teams and shapes (the test harness). The level is read by the Rust scene (`bc2_scene`, under a second where the retired Python loader took 6-15 s; required since round F1a) | `tests/test_level.py`: counts against `tests/level_snapshot.json`; `tests/test_scene_native.py`: the Rust scene against the Levels recorded from the Python loader (`scene_golden.json`), piece by piece |
| `fbrb.py` | `.fbrb` bundles without unpacking: the entry list (the header alone, fast), single entries (the payload streamed up to them) and `read_many` for many bundles; `pack` / `pack_many`, FbrbTool's pack of an unpacked folder. `unpack`, FbrbTool's unpack (in the Rust core for every bundle, the engine of `fbrbtool.py`). Runs in the Rust core (required since round F1a: the Python reader and the FbrbTool.exe fallbacks retired) | the test harness's tests: bundles built in the test; the same entries as FbrbTool on sp_009; `tests/test_fbrb_native.py`: the retired Python reader's answers (recorded: `fbrb_golden.json`) on every bundle of the game copy; `tests/test_fbrb_pack_native.py`: the Rust packer's bundles FbrbTool's, byte for byte, on every bundle of the game copy; `tests/test_fbrb_unpack_native.py`: the in-process unpack's files and manifest FbrbTool's on built, odd and damaged bundles and the game copy |
| `native.py` | the Rust core (`bc2_native`): finds it (built or downloaded into this folder, else installed), uses it only when its source fingerprint is the checkout's (`bc2_native.json` caches the checkout's), `require` for the pieces with no Python twin (texture conversion, NavKit's grid walks, the conversions, the core formats - `dbx`, `fbrb`, `terrain`, `water`, `collision`, `level` -: `NativeMissing` saying how to get it); the fingerprint `rust/build_native.py` bakes in. The built binaries: `find_binary` (`bin\` first, then the build folder), `target_dir` (cargo's build folder for this checkout, `rust-targets\<checkout>`, round D1), and the command lines: `cli_command(tool)` gives `[bin\bfbc2.exe, tool]` while the binary is this checkout's, else `[python, the tool's .py]` (`CLI_TOOLS`; `BFBC2_CLI_PYTHON=1` the Python); the retired ones (`RETIRED_CLI`: `graphstats`, `prepare_level`) only the binary, else `CliMissing` (README.md, "bfbc2.exe") | `../tests/test_native_required.py`: no module, a stale one, the matching one; the fingerprint; the download of `bfbc2.exe` |
| `fbrbtool.py`, `dbxedit.py` | FbrbTool's (`unpack`, `pack`, `list`, `big`) and DbxEdit's (`xml`, `edit`, `import`, `check`, `roundtrip`, `fixslots`) commands run in process in the Rust core: `run`, `run_many` (all cores), one function per command, `run_cmd` as a drop-in for `subprocess.run`; the same files, messages and exit codes as the retired exes (round R4) | `tests/test_fbrbtool.py`, `tests/test_dbxedit.py`: against the exes' recorded answers |
| `atomicio.py` | whole-file writes that never leave a half-written target (a temporary file in the target's folder, then `os.replace`), and `locked`, a lock between processes; used for every write into the game copy and for the caches | `../tests/test_runner_parallel.py` (`locked` across three processes) |
| `appicon.py` | the suite's application icon for a tkinter window (the hub): `BFBC2_APP_ICON`, `design\icons\local\app.ico`, `design\icons\app.ico`, else none (round I1) | |
| `viewer.py` | the 3D view: triangles and lines tagged with object ids and layers, orbit and fly camera, GPU picking with the world point, an overlay for links and measurements, ImGui panels (the Navigation Studio's; the Map Inspector's until GR1) | the Navigation Studio's screenshot runs |
| `navdata.py` | a Kynapse path-data file as the 3D tools draw it: walkable cells (ground heights from the terrain), area boundaries, the route graph and its islands; a cache per file; cell comparison of two files | `tests/test_navdata.py` |
| `navpath.py` | the path test: a route between two points over a file's route graph (costs from the stored edges), or why there is none (no node near, different islands) | `tests/test_navdata.py` |
| `navtune.py` | navigation side files (`<level>.navtune.json`): the edits made to a level's AI navigation, their author (the PC's name) and the base they were made on | `tests/test_navtune.py` |
| `pick.py` | the level picker the 3D tools show when started without a level | `../tests/test_viewers.py` |
| `caches.py` | the on-disk caches in `%LOCALAPPDATA%\bfbc2-tool-suite\cache`: their folders and size caps, `prune` (the least recently used entries deleted down to a cap; a writer's temporary file, an entry in use or changed meanwhile never; under a lock between processes), `maybe_prune` (at most every 15 minutes), `touch` (an entry marked used); the project caches in Project OPFOR BFBC2's `work\` (navdata.load's: `prune_project_cache`); the logs (`day_log`: a day's next part past the per-file cap; `prune_logs`: 20 newest days per tool, per-tool and overall caps, never the session's files); `python -m bfbc2core.caches --list / --prune / --clear [name...]`, `--report` (every cache, the logs, every checkout's Rust build folder, OPFOR's `work\` by kind), `--prune-targets [--yes]` (the build folders whose checkout is gone); one budget over every cache, `BFBC2_CACHE_TOTAL_GB` (default 20, `prune_total`, round D1); `bfbc2.exe caches` is the same command line in Rust (README "Caches") | `tests/test_caches.py`: the order, the caps, a writer and a reader in other processes, two pruners at once, the owners' hooks, the command (temp folders only); `tests/test_logs_caches.py`: log rollover and caps, the project caches, the command |
| `errors.py` | error handling and logs for every tool: a log per tool and day in `%LOCALAPPDATA%\bfbc2-tool-suite\logs`, the cause and what to do when something fails, a window for the windowed tools | `tests/test_errors.py` |
| `paths.py` | where things are: Project OPFOR BFBC2 (`find_opfor`: the given folder, `OPFOR_ROOT`, then `project-opfor-bfbc2` beside or above the suite), its game copy (`game_dir`, `game_exe`, `find_game_exe`), the suite's built tools (`find_tool`), the sibling projects (`sibling`, `find_sibling`: bf1943-tool-suite, operation-rising-sun); `GameCopyNotFound`. Every tool's own locator (`navkit.find_opfor`, `shaderdb.find_opfor`, ...) is a wrapper over it, keeping its search order and messages (listed in the module) | `tests/test_paths.py` (a stand-in tree); `../tests/test_locators.py` (each locator against a reference checkout) |

```python
import sys; sys.path.insert(0, r'<suite>\core')
from bfbc2core import level
lvl = level.load('mp_005')                    # from Project OPFOR BFBC2's game copy (found next to the suite)
flags = [e for e in lvl.entities if e.category == 'capture point']
lvl.heightfield.height(-111.0, 163.3)         # terrain height there
```

The formats are described in the module docstrings and in `../DESIGN.md` section 7. Tests:
`python ..\run_tests.py quick` (no game data) and `python ..\run_tests.py game`.
